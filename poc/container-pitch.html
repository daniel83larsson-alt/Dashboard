Från oversedda skript till en spårbar plattform

Läget idag

Skript körs — men ingen vet vilken version

iCore har redan ett eget gränssnitt med runtime och kan köra och kompilera skript. Det som saknas är historik och spårbarhet — och en säker väg att låta fler (och AI) bidra med kod utan att riskera skarpa kundflöden.

🕳️

Ingen versionshistorik

Går inte att se vad som ändrades, när, eller av vem — och inte att rulla tillbaka en ändring som visar sig fel.

🧵

Allt sitter ihop

Utan tydliga gränser mellan stegen riskerar en ändring i ett skript att påverka fler kunder än den var tänkt för.

🙈

Ingen spårbarhet per fil

Går inte att i efterhand svara på "vilken kod bearbetade just den här ordern" — viktigt vid felsökning och kundfrågor.

🚫

Svårt att låta fler bidra

Utan versionering och tester vågar man inte öppna upp för att fler utvecklare — eller en AI — skriver kod som körs skarpt.

Lösningen

Fem byggstenar som hänger ihop

Inget av det här är exotiskt — det är etablerade mönster (Git som sanningskälla, Claim Check för stora meddelanden) satta ihop för just den här plattformen.

1

📦 Container — en gemensam entitet för alla sorters skript

API-klient, mappningsskript, databas-skrivare, förädlingssteg — alla blir en Container med samma hölje (git-adress, version, byggprocess, manifest), även om körningen skiljer sig under huven.

api-klientmappningsskriptdatabas-skrivareförädling
2

🌱 Grund-repo — reglerna kommer med från start

Ett nytt skript skapas inte från ett tomt blad. Det ärver en mall med iCores SDK inbyggd: hämta indata, trigga nästa event, samt det typade kontraktet för vad datan faktiskt innehåller.

hämtaIndata(event) // GET /events/{id}/fil + /kontext triggraNastaEvent(...) // POST /events
3

📨 Event + Claim Check — pekare, inte payload

iCore skapar ett event ("mappa order") som pekar ut komponent och filnamn — inte filen själv. Skriptet hämtar hem det den behöver via API när den faktiskt ska bearbeta det. Håller event lätta även när filerna är stora.

4

✅ Bygg och testa ≠ aktivera

Varje commit byggs och testas automatiskt — men blir bara tillgänglig i katalogen. Att en kunds pipeline faktiskt börjar använda en ny version är alltid ett eget, medvetet steg. Det är brytpunkten som gör allt annat säkert.

5

🤖 LLM-redigering — samma skyddsräcken, ny författare

En LLM (iCores egen, eller en kunds/partners) kan föreslå kod på en egen gren. Samma tester, samma granskning, samma medvetna aktiveringssteg som när en människa skriver koden — bara källan till förslaget som skiljer sig.

🕐

Versionshistorik på riktigt

Löser det konkreta problemet ni har idag — gratis via git, ingen egen historikmodell att bygga och underhålla.

🔍

Spårbarhet per fil

Varje event pekar ut exakt vilken komponent och version som bearbetade en specifik order — svarar på supportfrågor direkt.

🔒

Säkert att ändra en sak

En kunds pipeline pekar på en specifik version. Byt förädlingssteget för en kund utan att röra någon annans.

⚡

Snabbare att bygga nytt

Nya integrationer återanvänder befintliga Containers istället för att byggas från grunden varje gång.

Var vi står

Vad som redan finns — och vad som återstår

Det här är ett arkitekturförslag under utforskning, inte ett färdigt beslut. Vi vet ännu inte i detalj hur iCores runtime och event-API faktiskt är byggda idag.
