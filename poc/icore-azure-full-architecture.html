En bild: allt som behöver finnas i Azure för hela kedjan

Miljöer (Dev → UAT → Prod), mappningar separerade från koden men versionerade, två portaler, och lasttest drivet av agenter — samlat på ett ställe istället för utspritt över hela konversationen.

1 · Miljöerna

Dev → UAT → Prod, samma kod, tre lägen

Samma byggda artefakt flyttas mellan lägena — den byggs aldrig om på vägen. Tekniskt: deployment slots i samma Azure Function App, med slot-swap som promotion. Dev testas rakt mot funktionens egen URL (manuellt och med agenter). UAT och Prod ligger bakom API Management — samma gateway, samma policyer, så UAT faktiskt testar det Prod kommer uppleva.

2 · Mappningar separerade från koden

Ändra en mappning ska inte kräva en ny kodversion

Git förblir sanningen för historik — vem ändrade vad, när. Men det som Function-koden faktiskt läser vid körning är en separat, snabb datakälla, inte filer bakade in i kodpaketet. Två olika saker att driftsätta, två olika hastigheter.

Versionshistorik, PR-granskning
→config-pipeline

Blob Storage / App Configuration

↓ läses av
Vid varje anrop
Function App
Hämtar rätt mappnings-version för kund+steg, ingen omdeploy krävd

Konsekvens: en ändrad mappning går genom samma gren → granskning → godkännande-gate som allt annat, men driftsätts separat och snabbare än en kodändring i själva stegmotorn.

3 · De två portalerna

Läsa och skriva är olika jobb, olika personer

Läs — drift & felsökning

Felsökningsportalen

  • Frågar Application Insights (KQL) för status/tider per steg
  • Frågar iCore för vilken version som är aktiv per kund
  • Läser mappnings-JSON från konfigurationskällan (steg 2 ovan) för att visa den faktiska mappningen
  • Sök på ordernummer/korrelations-id — en specifik orders resa
Skriv — bygga & justera

Scenario-portalen

  • Skapar/ändrar mappnings-JSON — skriver till git, triggar config-pipeline
  • Drag-and-drop för sista-steget-justeringar, samma JSON-schema
  • Aktiverar en ny version för en kund — det mänskliga godkännande-klicket
  • Startar ett lasttest mot UAT (se nästa avsnitt)
4 · Lasttest med agenter

Alltid mot UAT, aldrig mot Prod

Azure Load Testing är den namngivna tjänsten — kör skriptade lastprofiler mot en URL, mäter svarstid/felfrekvens under belastning. Agent-delen sitter i två ändar av det: en LLM genererar realistiska, varierade testpayloads utifrån de faktiska mappnings-scheman (inte bara samma exempelorder om och om igen), och en LLM tolkar resultatet efteråt och flaggar avvikelser istället för att någon manuellt läser en graf.
